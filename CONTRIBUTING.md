# Изменения проекта

Для обсуждения ошибки или идеи создайте issue с ожидаемым поведением и воспроизводимым примером. Для ошибок интерфейса полезны размер экрана, браузер и скриншот без личных данных.

1. Создайте ветку от актуального `main`.
2. Сохраняйте структуру предметных модулей; правила приложения держите в service/domain, SQL — в repository, HTTP — в transport.
3. Добавляйте миграцию для изменения схемы. Проверяйте существующие данные, а не только пустую БД.
4. Проверьте изменение подходящими тестами. Полный набор и требования описаны в [DEVELOPMENT.md](docs/DEVELOPMENT.md).
5. В PR опишите проблему, итоговое поведение и выполненные проверки. При изменении интерфейса приложите скриншот.

Go форматируется `gofmt`. Для frontend используйте стиль окружающего кода. Не добавляйте `.env`, зависимости, логи и персональные данные. Шаблоны `.env.example` должны оставаться пригодными для нового клона.

При изменении backend перед production-выпуском пересобирайте Linux-бинарник и checksum (`make backend-build`). Изменения документации не требуют пересборки и деплоя.
