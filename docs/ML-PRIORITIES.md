## Архитектура первой версии

Python используется только при подготовке базовой модели. Обучающий скрипт работает на стандартной библиотеке, с фиксированным seed, без облачных API. Go загружает встроенный JSON-артефакт и выполняет inference и персональное обучение без отдельного ML-сервиса и без дополнительных сетевых запросов. Библиотеки ML на production-сервер не устанавливаются.

Два уровня: мультиномиальный наивный Байес классифицирует русский/английский текст по 7 категориям; логистическая регрессия предсказывает риск пропуска дедлайна. Неизвестный текст получает категорию «Прочее». Заголовок имеет удвоенный вес. Версия модели включает схему признаков и хеш фактических обученных весов/словаря. Повторное обучение с изменённым артефактом не переиспользует несовместимые личные поправки.

Числовые признаки: оставшееся время, исходное время до дедлайна, оценка длительности, число активных задач, число других сроков в ближайшие сутки, наличие/длина описания, повторяемость, пользовательская важность, выходной день дедлайна (UTC), вероятности категорий. Числа нормированы и ограничены. Фактическое время завершения и исход задачи не входят в признаки.

Итоговый балл = 50% близость дедлайна + 30% прогноз риска + 20% важность. Приоритет: высокий (65+), средний (40+), низкий. Просроченная задача имеет известный исход, а не «предсказанную» просрочку. Выполненные задачи не попадают в рекомендации. Пользовательская важность и длительность имеют значения по умолчанию (обычная, 30 минут), редактируются в форме задачи. Риск — оценка модели, не доказанная вероятность и не объективная важность.

Основа линейного обучения и регуляризации: https://scikit-learn.org/stable/modules/sgd.html . Реализация использует ту же математическую постановку log-loss + L2, без зависимости от sklearn в runtime.

## Персонализация и корректность

Для текущей редакции задачи сохраняется снимок признаков **до известного исхода**. Снимок не перезаписывается при просмотре/выполнении. Редакция определяется содержанием, дедлайном, длительностью, важностью и повторяемостью, а не completed_at.

Метки: завершена не позже срока → 0; завершена позже срока или остаётся открытой после срока → 1; будущая незавершённая → метки ещё нет. Завершённые исторические задачи без своевременного снимка показываются в статистике, но не используются для обучения — их исход уже известен.

Персональные поправки обучаются на последних 500 допустимых снимках с регуляризацией к общей модели и ограничением изменения каждого веса. Пересчёт выполняется только при изменении отпечатка обучающих примеров. Это исключает повторный учёт просмотров, позволяет убрать устаревшую метку при переносе, переоткрытии и удалении и восстановить обучение после перезапуска. Смена версии модели сбрасывает несовместимые поправки.

Обновление профиля и снимков сериализовано транзакцией по пользователю. Пользователь не задаёт user_id в API; ID берётся из существующего auth middleware. Снимки и веса разделены по аккаунтам и удаляются вместе с ними. Тексты не передаются третьим сторонам; снимки содержат только признаки, revision и ID.

Фоновая синхронизация работает раз в минуту; после изменения задачи выполняется best-effort синхронизация, а ошибка логируется и повторяется worker-ом. Обычное представление задач продолжает работать при недоступности ML. API ранжирования возвращает версию, число личных примеров, причины и статистику категорий, а не скрывает ошибки под успешным ответом.

## Оценка и границы

Метрики синтетической выборки измеряют воспроизведение заданного генератором процесса. Они **не подтверждают** точность на реальных пользователях. До накопления реальных исходов интерфейс обозначает базовую оценку. Реальная проверка требует временного разделения снимков и исходов; алгоритм не использует данные другого пользователя для его персональных поправок.

Граф зависимостей и топологическая сортировка не входят в первую версию. Модуль ранжирования отделён от CRUD задач: в будущем можно добавить этап выбора доступных задач по DAG перед сортировкой по текущему баллу.

## Контракт и запуск проверок

`POST/PATCH /tasks` принимает `importance` (1–3, по умолчанию 2) и `estimated_minutes` (5–480, по умолчанию 30). Параметры сохраняются, возвращаются в ответах и наследуются повторяющимися задачами.

`GET /api/v1/tasks/priorities` требует Bearer-сессию и игнорирует подставленный query `user_id`. Ответ: `items` (ID, категория, score 0–100, high/medium/low, оценка риска, причины, версия), `recommendations` (до 3 активных задач из высшей присутствующей группы), `categories` (известные/просроченные исходы, отдельно позднее завершение и открытая просрочка), `personal_samples`, `personal_state`, `model_source`, `trained_at`. Выполненные задачи не рекомендуются. HTTP-кеширование ответа запрещено.

```sh
# Go, Node >=22.18, Python 3, Docker; запуск только на локальной тестовой базе
bash scripts/check_ml.sh
```

Команда проверяет воспроизводимость, Python/Go parity, все Go-тесты, race detector нового модуля, vet, frontend-тесты и сборку. Затем сама создаёт отдельные PostgreSQL/Redis со случайными портами, запускает backend, проверяет реальные HTTP-сценарии и повторяет чтение модели после остановки/старта процесса. Тестовые контейнеры и каталог удаляются автоматически. `scripts/ml_smoke.py` отдельно допускает только localhost.

`python3 ml/train.py` переобучает базовую модель, `--check` проверяет совпадение артефакта. Метрики — `ml/metrics.json`, встроенный артефакт — `internal/features/priorities/model/baseline.json`.

## Выпуск и границы дальнейших изменений

Миграция `0011_ml_priorities` добавляет только новые поля/таблицы. Отдельно проверены применение к существующей задаче, значения по умолчанию и up/down/up. Откат миграции удаляет личные ML-профили и снимки, но сохраняет сами задачи. Для rollback приложения безопаснее оставить добавленную схему.

Бинарник собирается локально `make backend-build` и доставляется через git; runtime-образ не требует Python или ML-пакетов. Старое представление по времени остаётся доступным независимо от расчёта приоритетов. Новые версии модели автоматически начинают совместимую историю заново; старые наблюдения с известным исходом не пересчитываются задним числом.

Следующая ступень проверки качества — временная offline-выборка реальных снимков: сравнить Brier/log-loss общей и персональной моделей, их калибровку и соблюдение сроков после рекомендаций. В текущем выпуске synthetic AUC не трактуется как доказательство качества на пользователях. DAG можно добавить отдельным фильтром доступных задач перед текущим ранжированием.


## Результат проверки первой версии

Полный `scripts/check_ml.sh` выполнен успешно: 3 Python-теста, воспроизводимое обучение, Go unit/regression-тесты, race detector ML-модуля, vet, 12 frontend-тестов, production-сборка frontend, HTTP/SQL сценарии и восстановление после перезапуска. Дополнительно проверены миграция up/down/up с существующей задачей, прежний smoke-тест напоминаний/отчётов/refresh, интерфейс 390×844 без горизонтального переполнения и работа собранного linux/amd64 бинарника в runtime-окружении. Синтетические метрики: ROC-AUC 0.733524, Brier 0.176882 против 0.206458 у постоянного прогноза. Это не оценка на реальных пользователях.
